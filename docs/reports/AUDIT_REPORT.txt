SECTION 3 - CACHE INTEGRATION DETAILS
================================================================================

Cache Type: In-Memory (request-dedup.ts Map)
- Used for: Private user-specific data (judge, team, admin)
- TTL: 5 minutes (private:team, private:assignments), 2 minutes (private:submission, private:results)
- Scope: Per-tab, per-session
- Cleared on: Tab close, logout (clearCache()), cache invalidation
- Survives full reload: NO (by design for private data — re-authorization required)

Cache Type: Persistent (localStorage/sessionStorage via persistent-storage.ts)
- Used for: Public data (event, schedule, criteria, problem statements, announcements)
- TTL: 30 min (event, problem statements), 5 min (schedule, criteria), 45s (announcements)
- Scope: Per-browser, persists across full reloads
- Cleared on: TTL expiry, tab close (sessionStorage), manual clear
- Survives full reload: YES

Cache Integration Points:
1. Judge Dashboard (JudgeDashboardClient.tsx)
   - Key: privateDashboardKey(userId, "judge") → v1:private:<userId>:dashboard:judge
   - Fetch: getCachedJudgeDashboard() server action
   - Policy: private:assignments (5 min TTL, memory only)
   - User-scoped: different judges never share cache

2. Team Dashboard (team-dashboard-client.tsx)
   - Key: team:<teamId>:dashboard
   - Fetch: getCachedTeamData({ teamId }) server action
   - Policy: private:team (5 min TTL, memory only)
   - Team-scoped: team data shared appropriately among team members

3. Announcements Banner (AnnouncementBanner.tsx)
   - Key: publicAnnouncementsKey(audience) → v1:public:<audience>:announcements
   - Fetch: getActiveAnnouncements(audience) server action
   - Policy: public:announcements (45s TTL, sessionStorage)

4. Schedule Page (schedule/page.tsx)
   - Key: public:schedule:<eventId>:schedule
   - Fetch: getCachedPublicSchedule(eventId) server action
   - Policy: public:schedule (5 min TTL, localStorage)
   - Falls back to hardcoded data if cache/API fails

5. Public Data Server Actions (cached-public.ts)
   - getCachedPublicEvent(eventId) → v1:public:<eventId>:event
   - getCachedPublicSchedule(eventId) → v1:public:<eventId>:schedule
   - getCachedPublicCriteria(roundId) → v1:public:<roundId>:criteria
   - getCachedPublicProblemStatements(eventId) → v1:public:<eventId>:problem-statements
   - getCachedPublicAnnouncements(audience) → v1:public:<audience>:announcements
   - NOTE: Only schedule page is wired. Ready for use when other public
     pages fetch from Supabase.

SECTION 8 - NETWORK FAILURE RECOVERY STRATEGY
================================================================================

1. Timeouts: Supabase admin client (10s), server client (8s) via AbortSignal
2. Bounded retries: request-dedup.ts retries (default 2 attempts) with
   exponential backoff (1s base, jitter, capped at 30s)
3. AbortSignal: Supported in fetchWithDedupe for request cancellation
4. Graceful fallback: useCachedData shows last known data on fetch failure
   (never crashes UI); background revalidation on tab focus
5. Realtime recovery: Single-flight refresh after channel settles (200ms
   delay); fallback polling when realtime is disconnected; polling paused
   in background tabs
6. No offline write queue: By design — offline writes must never silently
   appear as submitted. Users see online/offline status via navigator.onLine.

================================================================================
SECTION 7 - PROTECTION AGAINST DUPLICATE SUBMISSIONS
================================================================================

- Database-level idempotency: saveSubmissionDraft uses upsert with
  onConflict("form_id, team_id"); submitFinalSubmission uses upsert with
  onConflict("form_id, team_id")
- Request deduplication: fetchWithDedupe single-flight ensures identical
  concurrent requests share one Promise
- No automatic retries on non-idempotent writes without DB-level protection
- Draft cleared after successful submission
